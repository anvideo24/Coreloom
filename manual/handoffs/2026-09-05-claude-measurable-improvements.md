# Claude 인계 — 기능별 개선 목표와 검증 화면

작성일: 2026-09-05 · 상태: 계획 초안·부분 기준 측정 인계. 제품 구현 완료 보고가 아님.

## 이 문서부터 읽는 이유

사용자는 기능별 목표·계획·체크리스트·완료 증거를 자신도 쉽게 볼 수 있게 만들고 싶어 한다. 실제 코딩은 Claude Sonnet으로 진행하고, 계획·중간 리뷰는 Codex가 맡는 방식으로 요청했다. 이번 요청은 Claude에서 이어갈 수 있도록 인계 자료를 준비하는 것이다. Codex는 여기서 제품 구현을 시작하지 않는다.

## 읽을 순서

공용 원문의 읽기 순서 정본은 [working-method AGENTS.md](https://github.com/anvideo24/working-method/blob/main/AGENTS.md)다. 아래는 이 작업의 파일 위치 안내이며 규칙 사본이 아니다.

1. `C:\dev\working-method\AGENTS.md` → `HOW.md` → `LESSONS.md` → `RULES.md`. GitHub main과 비교해 최신 원문을 읽되, 아래 로컬 제안서를 잃지 않는다.
2. Coreloom [RULES.md](../../RULES.md) → [AGENTS.md](../../AGENTS.md) → [운영 매뉴얼](../00-coreloom-매뉴얼.md).
3. [개선 목표·계획·28개 검증 항목](../../docs/superpowers/plans/2026-09-05-measurable-improvements.md). 목표와 검사 항목의 원본은 이 문서다.
4. [개선 전 기준 측정](../../docs/quality/baseline-2026-09-05.md). 당시 관찰값과 재현 방법이며 현재 상태를 대신하지 않는다.
5. `C:\dev\working-method\proposals\measurable-feature-verification.md`. 공용 규칙 변경 제안이며 아직 현행 규칙이 아니다.
6. 구현 착수 시 `apps/web/AGENTS.md`, `apps/web/CLAUDE.md`, 수정 경로에 적용되는 추가 지침을 읽는다. 화면 작업은 적용되는 디자인 스킬과 제품 토큰을 먼저 확인한다.

## 로컬 자료 위치 — main에서 안 보일 수 있음

| 저장소 | 인계 준비 시 브랜치 | 보존된 자료 커밋 |
|---|---|---|
| `C:\dev\Coreloom` | `codex/verification-plan-stage1` | `67bcdb5` — 개선 계획·기준 측정 |
| `C:\dev\working-method` | `codex/verification-plan-stage1` | `1682a53` — 공용 변경안 |

이 인계 문서와 매뉴얼 연결은 Coreloom 위 브랜치의 후속 문서 커밋이다. 파일별 최신 커밋은 Git에서 확인한다. 이 인계 시점에 위 자료는 로컬에만 보존했고 원격 push·PR·main 병합·배포를 하지 않았다. GitHub main만 읽으면 계획이 없을 수 있다. 다른 PC나 클라우드 Claude라면 파일 전달 또는 별도로 승인된 Git 게시가 먼저 필요하다.

두 저장소는 공개다. 실제 고객·연락처·계좌·자격 정보·Funnel 주소를 인계나 증거에 넣지 않는다. 공유 폴더에서 브랜치를 무작정 전환하지 않는다. 시작 시 현재 브랜치·변경·최신 main과의 차이를 확인하고, 새 구현 브랜치에 필요한 문서만 안전하게 가져온다. 이 문서 작성만으로 최신 main 동기화나 서버 재시작이 필요한 것은 아니다.

## 어디까지 했나

- F01–F07의 기능 목표와 총 28개 검증 항목을 문서화했다. 제품 코드·DB·설정은 변경하지 않았다.
- PC 고객사 폼의 표시 입력 요소 21개·필수 요소 1개, 닫기→재열기 초안 손실을 관찰했다. 직접 입력량 전체를 측정한 것은 아니다.
- 가상 데이터 함수 시험으로 월말 누락, 청구일/입금 예정일 집계, 동일 고객사 프로젝트 간 견적 단계 혼입을 재현했다. 실고객 데이터 오류를 입증한 것은 아니다.
- 전체 고객사→견적 경로, 실제 휴대폰, 대표의 승인 판단 시간·AI 상태 이해도는 미측정이다. 0 또는 통과로 채우지 않는다.
- 28개 검사 ID 중복 없음, 문서 간 상대 링크와 민감정보 패턴 검사를 확인했다. 이는 제품 기능 검증 통과가 아니다.
- Claude Sonnet 코딩 실행과 Codex 코드 리뷰는 아직 수행하지 않았다. 모델 사용 가능 여부는 실제 실행 시 다시 확인한다.

## 다음에 할 일

직전 제안은 **2단계 F07: 기존 `/admin/manual/progress`에 목표·검증 현황 조회를 추가하는 최소 구현**이다. 전체 7개 기능 동시 구현이나 ERP 전면 개편이 아니다. 확정된 승인은 1단계 계획·비파괴 측정과 이번 인계 문서 준비다. 사용자가 Claude에 별도로 구현을 지시하면 그 지시 범위로 진행하고, 단순히 이 문서를 읽으라고만 했다면 F07 범위·완료 기준을 짧게 제시하고 승인을 받는다.

F07의 상세 완료 기준·대상 파일은 계획 원본을 따른다. 기존 매뉴얼 입구를 활용하고, 기능→목표→검사→증거를 읽을 수 있게 한다. 결과 없는 항목도 남기며 ‘구현’, ‘검증 통과’, ‘사용 환경 반영’을 구분한다. 기존 진행 표의 ‘완료’를 새 검사의 통과로 자동 승격하지 않는다. 원본을 구조화할 경우 상태 사본 두 벌을 만들지 않는다.

공용 변경안은 사용자 문구 승인 후 working-method 정본에 편입한다. 제품 쪽에 공용 원문을 복제하지 않는다. F05 집계 수정·F02 초안 보존 등은 후속 묶음이며 F07 승인에 자동 포함되지 않는다.

## 구현·검증 인계 시 주의

- 실제 코딩은 요청된 Claude Sonnet으로 한다. 다른 모델 또는 유료 API로 임의 대체하지 않는다. Codex 리뷰를 하지 않았다면 했다고 쓰지 말고, 사용자에게 변경 커밋·검사 결과·남은 위험을 전달해 리뷰를 연결한다.
- 개발 PC 기동·포트·마이그레이션 경계는 제품 AGENTS와 매뉴얼을 따른다. 계획을 읽기 위해 서버를 재시작하거나 DB를 변경하지 않는다.
- 테스트 데이터 생성, DB 변경, 외부 발송, 운영 배포는 인계받았다는 이유로 실행하지 않는다. 각 작업의 권한과 환경을 다시 확인한다.
- 구현 후 코드·영향받은 제품 규칙·운영 설명·진행 현황·변경 기록을 함께 갱신한다. 검사 실패를 우회해 main에 합치지 않는다.
- 보고에는 구현 변경, 자동 검사, 실제 화면 확인, 사람 측정 대기, main/사용 환경 반영 여부를 구분한다. 사용자 시간은 실제 사용자 시험으로만 기록한다.

이 파일은 인계 시점의 안내다. 이후 상태는 계획의 결과·증거와 Git에서 확인하고 이 문서를 완료 상태의 별도 정본으로 사용하지 않는다.
