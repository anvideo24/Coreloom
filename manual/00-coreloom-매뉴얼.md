# Coreloom 운영 매뉴얼

## 이 매뉴얼의 목적

Coreloom은 강의·앱·온라인 서비스를 함께 운영하는 1인 창업자와 AI 에이전트 팀을 위한 비공개 운영 본부다. 회사 설립 준비, 고객사 수주·계약·청구, 매출·비용, 프로젝트 진행, 관련 기록의 근거 확인을 한 흐름으로 관리한다. 이 문서는 시스템 설명의 정본이며, 미래 배포본의 관리자 화면에서도 같은 원본을 표시한다. 공용 제품 규칙과 일하는 방식은 GitHub `anvideo24/working-method`다. Coreloom만의 지금 규칙은 [RULES.md](../RULES.md), 이 프로젝트 기동은 [AGENTS.md](../AGENTS.md)다.

## MVP의 업무 흐름

1. 대표가 개인사업자 설립 준비 항목과 증빙을 등록한다.
2. 고객사와 담당자를 등록하고, Recho 메일·통화·회의 기록을 필요할 때 프로젝트에 연결한다.
3. 대표가 견적서를 작성·수정해 PDF로 발송하고, 전자서명 또는 날인 계약 원본을 보관한다.
4. 대표와 AI 에이전트가 프로젝트 업무·일정·진행률·분할 청구 일정을 관리한다.
5. 대표가 청구·세금계산서·입금 상태와 사업별 매출·비용을 확인한다.
6. AI 에이전트가 제안한 합의·다음 할 일·위험을 Recho 근거와 함께 보고, 대표가 확정 또는 반려한다.

세부 MVP 범위는 [docs/mvp-scope.md](../docs/mvp-scope.md)를 따른다.

## 운영자 기본 원칙

- 금액과 승인 상태는 확정 전에 반드시 거래처·프로젝트·증빙을 확인한다.
- 잘못된 기록은 덮어쓰지 말고 정정 이력을 남긴다.
- 개인 정보와 재무 정보는 필요한 역할에게만 보이게 한다.
- 화면상 숫자와 실제 저장 데이터가 다르면 기록을 수정하기 전에 변경 이력과 권한을 먼저 확인한다.
- AI 에이전트의 결과는 대표가 확인·승인하기 전까지 확정된 거래, 공개물 또는 회사 결정으로 취급하지 않는다.
- Recho 기록의 최신 발언은 현재 결정의 후보일 뿐이다. 앞뒤 시간 맥락과 원문을 확인한 뒤에만 공식 결정으로 확정한다.

## 대표 로그인과 데이터 기반

- Coreloom은 Neon Auth의 대표 이메일 로그인과 서버 측 허용 이메일 검사 두 단계를 함께 사용한다. 인증은 됐지만 허용 이메일과 다른 계정은 운영 화면을 볼 수 없다.
- 개발 PC의 정식 기동은 `apps/web`에서 `npm run up`이다. 이 명령은 `main`이 깨끗하면 최신을 받고, 예전에 켜 둔 3000번 서버를 끈 다음 PC와 휴대폰용 주소를 같이 연다. 로컬 서버는 HTTP만 쓰며 PC 브라우저는 `http://127.0.0.1:3000/dashboard`를 연다. `/api/auth`는 PC의 `127.0.0.1`과 `localhost` Origin을 Neon이 기본으로 받는 `http://localhost:3000`으로 같게 본다. 휴대폰 Funnel은 HTTPS `:8443`이 로컬 3000으로 연결된다. Funnel이 바깥으로 열 수 있는 포트는 `443`, `8443`, `10000`뿐이다. Coreloom은 `:8443`을 쓰고, 숫자 없는 `443`은 끈다. `:10000`은 다른 앱이므로 건드리지 않는다. 휴대폰에서는 Tailscale 앱을 끈 채 모바일 데이터로 `:8443` 주소만 연다. Safari 또는 Chrome에서 홈 화면에 추가하면 단독 웹앱처럼 열린다. PC만 열 때는 `npm run dev`로도 된다. `npm run dev`를 켤 때도 `main`이 깨끗하면 최신을 먼저 받는다. Funnel 주소와 실제 호스트 이름은 채팅·로그·커밋·PR에 넣지 않는다. 이 주소는 대표만 쓰고 다른 사람에게 보내지 않으며, 로그인된 대표 계정만 들어올 수 있다. Funnel 주소는 localhost가 아니므로, 휴대폰 로그인이 막히면 Neon Console → Auth → Configuration → Domains에 `:8443`이 붙은 HTTPS 주소를 넣는다. `/api/auth`는 휴대폰 Funnel `:8443` Origin도 Neon이 받는 localhost Origin으로 바꿔 넘긴다. 다른 사이트 Origin은 바꾸지 않는다. `/setup`은 이 PC의 localhost에서만 저장된다. PC가 꺼져 있거나 서버가 꺼져 있으면 휴대폰에서도 열리지 않는다. 개발 서버를 바꾼 뒤에는 다시 켠다.
- Cursor Cloud Agent가 UI를 눈으로 확인할 때는 PC `npm run up` 대신 `apps/web`의 `npm run cloud:bootstrap`·`npm run cloud:dev`를 쓴다. Cursor 환경 Secrets에 `DATABASE_URL`(ai-development), Neon Auth·대표 이메일, `TEST_LOGIN_USERNAME`·`TEST_LOGIN_PASSWORD`를 두고, 브라우저로 `http://127.0.0.1:3000/sign-in`에 로그인한 뒤 대상 화면을 스크린샷·녹화한다. 비밀 값·실이메일은 채팅·커밋·로그에 남기지 않는다. `production` 연결은 쓰지 않는다. 절차 정본은 저장소 [AGENTS.md](../AGENTS.md) 「클라우드 에이전트 시각 검증」이다.
- 대표 운영 화면 셸은 [RULES.md](../RULES.md) 화면 셸 절이 정본이다. 지금은 좌측 사이드바를 고정해 열면 본문을 옆으로 밀고, 전역 AI 에이전트 패널과 작성 패널은 플로팅으로 뜬다. 좁은 화면은 하단 메뉴(개요·수주·재무·운영·더보기)와 아래 시트다.
- `/dashboard`에서 승인 대기·오늘 업무·연체 입금·미분류와 오늘 할 일 한 목록, 이번 달 입금·지급 추이, 진행 프로젝트의 견적·계약·청구 단계와 다음 할 일을 본다. 설립이 끝나지 않았으면 진행률도 함께 본다. 이 화면은 조회만 하며 발송·체결·입금 확정·비용 확정·AI 확정을 대신 실행하지 않는다.
- 개발 PC에서 처음 연결할 때만 `/setup`에서 Neon Auth 주소와 대표 이메일을 입력할 수 있다. 데이터베이스 연결 문자열은 스키마 작업을 시작할 때 별도로 연결한다. 이 화면은 운영 배포에서는 열리지 않으며, `.env.local`이 있으면 덮어쓰지 않는다.
- 개발용 스키마를 적용할 때만 `/setup/database`에 `ai-development` 연결 문자열을 추가한다. 기존 Auth 설정이나 기존 데이터베이스 연결 문자열은 이 화면에서 덮어쓰지 않는다.
- `/company-setup`은 대표 전용 개인사업자 설립 준비 화면이다. 상태, 증빙 위치 또는 링크, 확인 메모를 항목별로 저장하며 변경 이력도 남긴다. 같은 화면에서 견적·청구 INVOICE에 쓸 공급자·입금 안내(사업자등록번호·은행·계좌 등)를 회사 프로필로 저장하면 문서가 그 값을 읽는다. 프로필은 구역(회사 / 입금 안내)·2열로 정리하며, 목록+`+` 패널 면이 아니라 체크리스트 면이다 둔다. 증빙 위치 없이 항목을 완료로 바꿀 수 없다. 이 화면의 공식 안내 링크는 확인용이며, 과세 유형과 신고 일정의 최종 판단·신청·발급은 대표가 직접 진행한다.
- `/documents`에서 문서 목록을 보고 헤더의 `+`로 원본을 등록한다. 고객사만 연결하거나(사업자등록증 등) 프로젝트에 연결할 수 있다. 둘을 동시에 고르지 않는다. 설립 증빙·계약 원본·산출물·정산 자료의 원본 파일 또는 위치를 비공개로 보관한다. 올린 파일은 이 PC의 비공개 폴더에 두고 대표만 받을 수 있다. 수정은 기존 원본을 덮어쓰지 않고 새 버전으로만 남기며, 누가 언제 기록했는지는 이력으로 남긴다. 외부 공개는 하지 않는다.
- `/clients`에서 고객사 목록을 보고 헤더의 `+`로 등록한다. 상호·사업자등록번호·대표자명·과세 유형(일반/간이/면세)·거래 유형(매출/매입/매출·매입)·주소·업태·종목·홈페이지·대표 전화/이메일·계좌(은행·계좌·예금주·통장사본 위치)·사업자등록증 위치(링크)를 구역·2열 폼으로 받는다. 담당자는 고객사 상세에서 `+`로 추가하며 이름·역할·이메일·전화·관계 상태(활성/비활성)·세금계산서 수신 여부와 생성 이력을 남긴다. 개발 DB에는 0023·0025·0027 마이그레이션이 필요하다.
- `/clients-projects`에서는 프로젝트 목록을 보고 헤더의 `+`로 등록한다. 고객사·이름·상태·진행률·요약·시작일·목표 종료일을 구역·2열 패널로 받으며, 목록에서 상태·진행률을 고친다. 프로젝트 이름을 열면 업무·견적·계약·청구·문서와 오른쪽 Recho 근거·AI 제안을 한 화면에서 본다. 확정 전 AI 제안은 공식 결정으로 보이지 않으며, Recho API 동기화는 이 기능에 포함되지 않는다. 개발 DB에는 0024 마이그레이션이 필요하다. 다른 운영 화면의 리스트·패널·필드 격차는 `docs/operations/ops-screen-list-panel-rollout.md`에 적어 둔다.
- `/quotes`에서 견적 이력을 목록으로 본다. 헤더의 `+`로 넓은 원가 작성 패널을 연다. 상단에서 견적 주제·담당자·발행일·유효기간·부가세를 고르고, 고객용 탭은 발송될 A4 `INVOICE`를 보기만 한다. 항목 칸은 최대 6줄을 확보하고, 부가세 안내·합계·입금/공급자는 페이지 하단에 둔다. 공급자·입금 값은 `/company-setup` 회사 프로필에서 읽는다. 항목·설명·수량·단가·공급가액은 내부 원가 탭에서 편집하며, 오른쪽에는 실시간 합계와 버전 이력이 있다. 수정은 새 버전으로만 저장한다. 전자세금계산서 발행은 이 기능에 포함되지 않는다.
- 견적서 보기 화면에서 `메일 발송`으로 이동하면 수신자·제목·본문과 PDF 첨부 대상 버전을 확인한 뒤, 대표 승인 체크를 통해 발송을 요청한다. 발송 요청은 Resend API 키와 인증된 발신 메일이 로컬 비밀 설정에 연결된 경우에만 실행되며, 요청 접수·실패 이력은 견적 버전별로 보관한다. 요청 접수는 수신 완료를 뜻하지 않으므로 실제 수신은 수신자 메일함 또는 이후 전달 상태에서 확인한다.
- 개발 PC에서 처음 Resend 발송 키를 연결할 때만 `/setup/email`에 API 키를 입력한다. 키는 이 PC의 `.env.local`에만 저장되고 저장소·매뉴얼·채팅에는 남지 않는다. 기본 테스트 발신 주소로 동작을 확인한 뒤, 실제 고객사 발송 전에는 Resend에서 인증한 회사 발신 도메인으로 교체한다.
- `/contracts`에서 계약 이력을 목록으로 보고 헤더의 `+`로 견적 버전을 골라 계약 초안을 만든다. 계약번호·효력 시작·종료일·자동갱신을 초안·상세에서 남길 수 있다. 날인 스캔 원본의 보관 위치 또는 링크를 기록한 뒤에만 대표 승인으로 체결할 수 있다. 체결된 버전은 덮어쓰지 않으며, 수정은 새 버전으로만 남긴다. 전자서명 공급자는 선정 전까지 연결하지 않는다. 파일 원본 업로드는 이 기능에 포함되지 않는다. 개발 DB에는 0025·0026 마이그레이션이 필요하다.
- `/billings`에서 청구·반복 일정을 목록으로 보고, 헤더 `+`로 단건 청구(`?new=1`) 또는 반복 청구(`?new=series`) 패널을 연다. 체결된 계약에 착수금·중도금·잔금 또는 월 반복 일정을 등록한다. 단건에는 청구번호·PO(발주번호)를 선택으로 둔다. 반복 청구는 시작일부터 종료일까지 매달 예정 청구를 한 번에 만들며, 한 번에 최대 24개월이다. 각 금액은 통화(KRW), 청구일, 입금 예정일, 확정 상태를 함께 가진다. 입금은 대표 승인 뒤에만 확인 처리하며, 확인된 금액은 덮어쓰지 않는다. 각 청구에서 `PDF 다운로드`와 `인쇄`로 부가세 별도 청구서를 받을 수 있고, `메일 발송`은 대표 승인 체크와 Resend 연결이 있을 때만 실행된다. 요청 접수는 전달 완료를 뜻하지 않는다. 세금계산서 연계는 이후이며, 전자세금계산서 발행은 이 기능에 포함되지 않는다. 개발 DB에는 0025 마이그레이션이 필요하다.
- `/revenue`에서 매출 원장 목록을 보고 헤더 `+`로 매출을 등록하며, 사업 등록은 별 `+`(`?new=venture`)다. 계정과목은 `/accounts` 마스터의 수익 과목에서 고른다. 고객사 프로젝트 청구와 앱·구독 매출을 같은 원장으로 본다. 앱·구독은 사업으로 등록한 뒤 발생일·정산일·금액을 남기고, 연결하지 못한 건은 미분류로 표시한다. 매출 확정은 대표 승인 뒤에만 처리하며 확정된 금액은 덮어쓰지 않는다. 확정된 매출에 대해 환불을 등록하면 원래 금액을 덮어쓰지 않고 별도 환불 이력으로 남기며, 환불 합계는 원래 금액을 넘을 수 없다. 증빙 파일·결제 채널 자동 수집과 세금계산서 발행은 이 기능에 포함되지 않는다. 개발 DB에는 0026·0028 마이그레이션이 필요하다.
- `/expenses`에서 비용 원장 목록을 보고 헤더의 `+`로 등록한다. 계정과목은 `/accounts` 마스터의 비용 과목에서 고르며, 매입처 고객사(거래 유형이 매입 또는 매출·매입인 고객사) 또는 매입처 이름을 적을 수 있다. 고객사를 고르고 이름을 비우면 상호로 채운다. 고객사 프로젝트 또는 앱·구독 사업에 비용을 연결한다. 금액은 통화(KRW), 발생일, 지급 예정일, 확정 상태를 함께 가지며, 연결하지 못한 건은 미분류로 표시한다. 비용 확정은 대표 승인 뒤에만 처리하며 확정된 금액은 덮어쓰지 않는다. 자동 이체·급여·세금계산서 발행은 이 기능에 포함되지 않는다. 개발 DB에는 0026–0028 마이그레이션이 필요하다.
- `/accounts`에서 계정과목 목록을 보고 헤더의 `+`로 과목을 추가한다. 자산·부채·자본·수익·비용 구분을 두며, 처음 열면 기본 과목이 채워진다. 매출·비용 원장은 수익·비용 과목만 고른다. 복식 분개·전표·세무 대행은 포함하지 않는다. 개발 DB에는 0028 마이그레이션이 필요하다.
- `/tasks`에서 업무 목록·기한별 일정을 보고 헤더의 `+`로 등록한다. 고객사 프로젝트에 업무를 연결하고 기한과 완료 조건을 기록한다. 진행 중인 업무는 기한별 일정으로 보이며, 활성 AI 에이전트 시스템 계정에 배정할 수 있다. 완료는 대표가 조건을 확인한 뒤에만 처리한다. 완료된 업무는 덮어쓰지 않으며 배정도 바꾸지 않는다. Recho 캘린더 연동은 이 기능에 포함되지 않는다.
- `/agents`에서 AI 에이전트 목록을 보고 헤더의 `+`로 등록한다. 사람 Neon 계정과 다른 시스템 계정으로 이름, 목적, 허용 업무(자료 조사·초안 작성·업무 업데이트·승인 요청 초안), 접근 범위, 일하는 방식·답변 방식·절차·지침, 구독 모델(Claude/GPT·Codex/Cursor), 능력(기록 저장·외부 발송·금액·계약 확정·권한 변경, 기본 꺼짐), 상태를 구역(연결·기본·지침)·2열 패널로 보관한다. 대표가 요청·입력·결과와 승인·반려를 이력으로 남기며, 결정된 이력은 덮어쓰지 않는다. 능력에 켠 항목만 실행할 수 있다. 로그인, 자동 실행, 대표 승인함은 이 기능에 포함되지 않는다.
- `/timeline`에서 시간순 근거 목록을 보고 헤더의 `+`로 Recho 메일·통화·회의를 프로젝트의 근거로 연결한다. 원문 식별자, 발생 시각, 연결 이유를 보관하고 시간순으로 보여 주며, 원문 링크가 있으면 새 창에서 연다. Coreloom은 원문을 복제하거나 수정하지 않는다. Recho API 동기화는 이 기능에 포함되지 않는다.
- `/proposals`에서 미확정·결정 이력을 보고 헤더의 `+`로 근거 기록에 연결된 AI 제안 초안을 등록한다. 종류는 현재 합의·다음 할 일·위험이며, 근거가 없으면 등록하지 않는다. 대표가 원문을 확인한 뒤에만 확정 또는 반려하고, 확정 전에는 공식 결정으로 보이지 않는다. 결정된 제안은 덮어쓰지 않는다. 자동 생성, 계약 체결, 외부 발송은 이 기능에 포함되지 않는다.
- `/admin/manual`은 카테고리 카드로 고르는 입구다. 규칙(공용 규칙·이 제품 규칙), 일하는 방식(일하는 방식·배운 것), 운영(운영 설명·시스템 진행 현황·역할별 운영 절차·변경 기록)으로 나누고, 긴 원본은 칸을 고른 뒤에만 연다. 공용 문서는 `working-method` 저장소 원본을, 나머지는 이 저장소 원본을 읽기 전용으로 본다. 배포 버전·매뉴얼 원본 커밋을 함께 표시한다. 시스템 진행 현황에서는 기능별 구현 상태를 표로 추적하며, 기능이 추가되거나 상태가 바뀌면 같은 커밋에서 갱신한다. 화면에서 편집하지 않으며, 권한 없는 계정은 볼 수 없다.
- 대표 계정은 Neon Console에서 직접 만든다. 계정에 비밀번호가 없는 경우 `/auth/forgot-password`에서 대표 이메일로 설정 링크를 요청한다. 공개 가입은 켜지지 않으며, 이메일·비밀번호·연결 문자열·쿠키 비밀값은 저장소나 매뉴얼에 기록하지 않는다.
- 스키마를 바꾸면 같은 변경에 drizzle 마이그레이션을 둔다. 개발 PC에서는 `apps/web`에서 `npm run db:migrate`(또는 `tsx scripts/migrate.ts`)가 필요할 수 있다. 2026-09-04 기준 `ai-development`에는 0000–0024가 적용되어 있다. 코드에는 이어서 0025(고객사 과세유형·계좌, 계약 기간·자동갱신, 청구번호·PO), 0026(계약번호, 매출·비용 계정과목, 비용 매입처 이름), 0027(고객사 거래 유형, 비용 매입처 고객사 연결), 0028(계정과목 마스터·원장 FK)이 있다. 0025–0028이 없으면 고객사·계약·청구·원장·계정과목의 새 칸이 비거나 저장이 실패할 수 있다. 적용 여부는 이 클라우드가 아니라 개발 PC에서 확인한다.
- 스키마 변경은 `ai-development`에서 먼저 검증한다. `production` 적용과 복구는 대표의 그 시점 승인 없이는 실행하지 않는다.
- 백업은 자동화하지 않는다. 운영 변경 전후에 `docs/operations/neon-branch-and-backup-runbook.md`의 수동 절차를 따른다.

## 고객사 프로젝트 운영

1. 고객사·담당자·사업·프로젝트를 연결한다.
2. 견적서의 버전을 관리한다. 발송한 PDF와 이메일 발송 이력은 변경하지 않는다.
3. 계약을 전자서명 또는 날인으로 체결하고 최종 원본을 보관한다.
4. 착수금·중도금·잔금 또는 반복 청구 일정을 등록한다.
5. 프로젝트 화면에서 진행률·업무·문서·청구와 Recho 타임라인·AI 제안을 함께 확인한다.
6. 전자세금계산서와 입금은 외부 발행·수신 결과가 확인된 뒤에만 완료 처리한다.

## 관리자 매뉴얼 화면

대표는 `/admin/manual`에서 규칙과 운영 설명을 읽기 전용으로 본다.

- **홈은 고르는 입구다.** 카드 세 묶음(규칙·일하는 방식·운영)으로 나뉘고, 각 카드에는 한 줄 설명과 원본 파일 이름이 붙는다. 홈에 긴 원문을 펼치지 않는다.
- 카드를 고르면 그 원본이 열린다. 원본 화면 위에는 「매뉴얼 홈」으로 돌아가는 길이 있다.
- 이 화면은 Markdown 원문을 렌더링한다. 화면용 HTML 사본을 별도 정본으로 두지 않는다.
- 공용 규칙·일하는 방식·배운 것은 `working-method` 저장소에서 읽는다. 그 저장소는 Coreloom과 같은 부모 폴더에 클론한다. 찾지 못하면 그 칸은 「저장소가 아직 없다」고 밝히고, 빈 화면처럼 보이게 하지 않는다.
- 상단에는 배포 버전과 매뉴얼 Git 커밋을 표시해, 현재 화면의 설명이 어떤 배포본 기준인지 알 수 있게 한다. 원본 문서마다 그 파일의 마지막 커밋을 따로 보여 준다.
- 화면에서 직접 편집하지 않는다. 문서 변경은 저장소 커밋과 배포로 반영한다. 나중에 화면 편집기를 만들더라도 저장은 git 커밋이어야 한다.
- 일반 사용자와 권한 없는 사용자는 접근할 수 없다. 현재 관리자 역할은 대표 로그인과 같다.

## 매뉴얼 갱신 절차

1. 기능·규칙·운영 절차가 실제로 바뀐 경우에만 관련 Markdown을 고친다.
2. `manual/CHANGELOG.md`에 이유와 영향을 짧게 기록한다.
3. 문서의 링크와 실제 기능·화면을 확인한다.
4. 코드와 문서를 같은 변경으로 커밋·배포한다.
5. 배포 후 관리자 화면에서 최신 문서와 배포 버전이 함께 보이는지 확인한다.
