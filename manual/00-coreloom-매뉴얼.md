# Coreloom 운영 매뉴얼

## 이 매뉴얼의 목적

Coreloom은 강의·앱·온라인 서비스를 함께 운영하는 1인 창업자와 AI 에이전트 팀을 위한 비공개 운영 본부다. 회사 설립 준비, 고객사 수주·계약·청구, 매출, 프로젝트 진행, 관련 기록의 근거 확인을 한 흐름으로 관리한다. 이 문서는 시스템 설명의 정본이며, 미래 배포본의 관리자 화면에서도 같은 원본을 표시한다.

## MVP의 업무 흐름

1. 대표가 개인사업자 설립 준비 항목과 증빙을 등록한다.
2. 고객사와 담당자를 등록하고, Recho 메일·통화·회의 기록을 필요할 때 프로젝트에 연결한다.
3. 대표가 견적서를 작성·수정해 PDF로 발송하고, 전자서명 또는 날인 계약 원본을 보관한다.
4. 대표와 AI 에이전트가 프로젝트 업무·일정·진행률·분할 청구 일정을 관리한다.
5. 대표가 청구·세금계산서·입금 상태와 사업별 매출을 확인한다.
6. AI 에이전트가 제안한 합의·다음 할 일·위험을 Recho 근거와 함께 보고, 대표가 확정 또는 반려한다.

세부 MVP 범위는 [docs/mvp-scope.md](../docs/mvp-scope.md)를 따른다.

## 운영자 기본 원칙

- 금액과 승인 상태는 확정 전에 반드시 거래처·프로젝트·증빙을 확인한다.
- 잘못된 기록은 덮어쓰지 말고 정정 이력을 남긴다.
- 개인 정보와 재무 정보는 필요한 역할에게만 보이게 한다.
- 화면상 숫자와 실제 저장 데이터가 다르면 기록을 수정하기 전에 변경 이력과 권한을 먼저 확인한다.
- AI 에이전트의 결과는 대표가 확인·승인하기 전까지 확정된 거래, 공개물 또는 회사 결정으로 취급하지 않는다.
- Recho 기록의 최신 발언은 현재 결정의 후보일 뿐이다. 앞뒤 시간 맥락과 원문을 확인한 뒤에만 공식 결정으로 확정한다.

## 대표 로그인과 데이터 기반

- Coreloom은 Neon Auth의 대표 이메일 로그인과 서버 측 허용 이메일 검사 두 단계를 함께 사용한다. 인증은 됐지만 허용 이메일과 다른 계정은 운영 화면을 볼 수 없다.
- 개발 PC에서 처음 연결할 때만 `/setup`에서 Neon Auth 주소와 대표 이메일을 입력할 수 있다. 데이터베이스 연결 문자열은 스키마 작업을 시작할 때 별도로 연결한다. 이 화면은 운영 배포에서는 열리지 않으며, `.env.local`이 있으면 덮어쓰지 않는다.
- 대표 계정은 Neon Console에서 직접 만든다. 계정에 비밀번호가 없는 경우 `/auth/forgot-password`에서 대표 이메일로 설정 링크를 요청한다. 공개 가입은 켜지지 않으며, 이메일·비밀번호·연결 문자열·쿠키 비밀값은 저장소나 매뉴얼에 기록하지 않는다.
- 스키마 변경은 `ai-development`에서 먼저 검증한다. `production` 적용과 복구는 대표의 그 시점 승인 없이는 실행하지 않는다.
- 백업은 자동화하지 않는다. 운영 변경 전후에 `docs/operations/neon-branch-and-backup-runbook.md`의 수동 절차를 따른다.

## 고객사 프로젝트 운영

1. 고객사·담당자·사업·프로젝트를 연결한다.
2. 견적서의 버전을 관리한다. 발송한 PDF와 이메일 발송 이력은 변경하지 않는다.
3. 계약을 전자서명 또는 날인으로 체결하고 최종 원본을 보관한다.
4. 착수금·중도금·잔금 또는 반복 청구 일정을 등록한다.
5. 프로젝트 화면에서 진행률·업무·문서·청구와 Recho 타임라인을 함께 확인한다.
6. 전자세금계산서와 입금은 외부 발행·수신 결과가 확인된 뒤에만 완료 처리한다.

## 관리자 매뉴얼 화면

공개 배포된 시스템에는 관리자 전용 `/admin/manual`을 둔다.

- 이 화면은 `manual/`의 Markdown 원문을 렌더링한다.
- 메뉴에는 개요, 역할별 운영 절차, 변경 기록을 둔다.
- 상단에는 배포 버전과 매뉴얼 Git 커밋을 표시해, 현재 화면의 설명이 어떤 배포본 기준인지 알 수 있게 한다.
- 화면에서 직접 편집하지 않는다. 문서 변경은 저장소 커밋과 배포로 반영한다.
- 일반 사용자와 권한 없는 사용자는 접근할 수 없다.

## 매뉴얼 갱신 절차

1. 기능·규칙·운영 절차가 실제로 바뀐 경우에만 관련 Markdown을 고친다.
2. `manual/CHANGELOG.md`에 이유와 영향을 짧게 기록한다.
3. 문서의 링크와 실제 기능·화면을 확인한다.
4. 코드와 문서를 같은 변경으로 커밋·배포한다.
5. 배포 후 관리자 화면에서 최신 문서와 배포 버전이 함께 보이는지 확인한다.

## 아직 정해야 할 것

- 금액 구간별 승인자 및 승인 단계
- 회계·세무·은행·카드 서비스 연동 방식
- 관리자 화면의 접근 방식: 이메일 허용 목록, SSO 또는 사내 계정
