## 범위와 역할

- 이번 단계: 공용 변경안, 제품별 검사 목록, 비파괴 기준 측정, 사용자 열람용 문서.
- 이번 단계 제외: 제품 코드·DB·설정 변경, 실제 업무 데이터 생성, 외부 발송, PR·배포, 전체 제품 일괄 변경.
- 지휘·리뷰·검증: Codex. 후속 실제 코딩: Claude Sonnet 한 작업 묶음씩. 사용자: 목표 승인과 사람의 판단·이해도 측정.
- Sonnet 구독 실행 시 실제 모델을 확인한다. 다른 모델·유료 API로 임의 대체하지 않는다. 이번 단계에는 실제 코딩이 없어 모델을 호출하지 않았다.
- 한 파일의 공동 변경을 보존하고 맡은 파일만 커밋한다. 제품 코드·제품 규칙·매뉴얼은 같은 변경으로 관리한다. 공용 저장소의 변경은 별도 커밋으로 연결한다.

## 공통 측정 조건 — 코어룸

환경 불일치 수정 승인에 따라 아래 표에 `필수 검증 환경`을 추가했다. 버전 2의 기존 검사 ID·목표값·검증 방법은 바꾸지 않고 기존 실제 시험/자동 시험 구분을 판정기가 읽도록 명시한 것이다. 쉼표로 나눈 환경은 모두 필요하며, 결과의 `environments`에 실제 증거가 포괄한 환경명만 같은 표기로 기록한다. `environment`에는 구체적인 측정 조건을 계속 남긴다. 자동 시험은 격리된 코드·모의 화면 검사이고, PC 브라우저·실제 휴대폰·실제 폴드 접힘/펼침·실제 개발 DB·대표 측정과 서로 대체되지 않는다. 환경명은 증거 작성자가 확인한 범위이며 이 필드 자체가 기기 접속이나 증거 진위를 자동 입증하지는 않는다. 과거 기록에 환경명을 추측해 채우거나 통과를 자동 승계하지 않는다.

1. 데이터는 UX 전용 가상 사례만 사용한다. 사람 판단 시험의 정답표는 시험 전에 고정하며, 수행자에게 미리 보여주지 않는다.
2. PC와 실제 휴대폰을 구별한다. 브라우저 폭 재현은 모바일 레이아웃 측정일 뿐 실제 기기 시험을 대체하지 않는다. 기기·브라우저·뷰포트·계획 버전·검증 코드 버전을 기록한다.
3. 사람 시간은 연습 1회 제외 후 동등 난이도 사례 5회로 중앙값·최소·최대·정확도를 남긴다. 네트워크 대기와 실제 조작 시간을 별도 기록한다. 전후 학습 영향과 작은 표본 한계를 표시한다.
4. 입력량은 사용자가 직접 값을 넣은 필드 수, 반복 입력 필드 수, 직접 입력 문자 수를 나눠 기록한다. 화면에 보이는 필드 수를 직접 입력량으로 대신하지 않는다.
5. 경로 전환은 페이지 이동·패널 개폐·탭 전환을 각각 센다. 왕복은 현재 작업을 떠나 선행 정보를 등록한 뒤 돌아오는 구간이다. 뒤로 돌아온 값이 유지되는지도 확인한다.
6. 미측정은 숫자 0이 아니다. 원인, 필요한 준비, 재개 조건을 함께 적는다. 사용자 측정은 AI가 대신 통과 처리하지 않는다.

## F01 · 고객사에서 견적 초안까지

목표: 같은 정보를 다시 쓰거나 고객사 등록 때문에 견적 작업을 잃지 않는다.

범위: 최소 고객사 생성, 견적 안에서 고객사 추가와 복귀, 고객사·프로젝트 연결 유지. 고객용 문서 포맷 교체는 제외한다.

기준: 고객사 입력 요소 21개·필수 1개(B01). 전체 경로의 직접 입력량과 왕복은 미측정(B06).

### 입력량 측정 기준 — 버전 2 승인

- 기본 사례는 신규 고객사 + 견적 1품목 + 고객용 설명·메모다. 담당자·프로젝트가 있는 흐름은 별도 사례로 기록하며, 기본 사례 결과로 그 연결 검사를 대신하지 않는다.
- 동일한 가상 내용·기본값·최종 저장 결과를 고정하고 직접 입력 필드 수·문자 수·중복 입력·클릭·화면 전환을 나눠 센다. 화면에 보이는 입력칸 개수는 직접 입력량이 아니다.
- 기존 PC 기록의 6필드·58자는 설명·메모를 포함한 특정 사례의 관측값이지 보편적 최소값이나 비교 전 기준이 아니다. 개선 전후 서로 다른 사례를 비교해 감소율을 만들지 않는다.
- 중복 입력 0개·고객사 등록을 위한 외부 왕복 0회·입력 손실 0건은 계속 확인한다. 감소율 보류가 다른 검사 기준의 완화를 뜻하지 않는다.
- 비교 가능한 개선 전 기록을 확보하기 전까지 F01-03은 보류다. 분모에서 제외하지 않고 결과 파일에는 `unverified`와 보류 이유를 남긴다. 과거 화면 재구축이나 실제 데이터 생성은 별도 승인 뒤에만 한다.

후속 구현 대상: clients-page-client.tsx, client-company-fields.tsx, quotes-page-client.tsx, quote-client-project-fields.tsx, 관련 actions와 회귀검사. 경로는 apps/web/src/components 및 해당 app/(private) 아래다.

### AI 상태와 반영 범위 — 버전 2 승인

| 분류 | 확인할 사실 | 뜻하지 않는 것 |
| --- | --- | --- |
| 답변만 | 대화에만 존재, 업무 기록 변경 없음 | 답변 문구만으로 저장·확정 완료 |
| 제안 저장(미확정) | 사람이 기존 제안 화면에 저장한 제안 기록이 존재 | 회사의 공식 결정이나 AI의 자동 저장 |
| 대표 확정 | 대표가 기존 제안을 확정하고 서버에 결정 기록·이력이 남음 | 계약 체결·메일 발송·업무 자동 실행 |

분류 시험은 위 세 상태를 각 2사례로 구성한다. 채점 자료는 `docs/quality/ai-status-classification-cases.md`를 따른다. 확정 제안은 승인 대기 목록에 억지로 넣지 않고 해당 상세·근거 타임라인에서 보여 준다. 실제 자료가 준비되지 않았으면 모의 사례임을 기록하고 실제 저장 검증으로 세지 않는다.

F04-03은 위 표의 대표 확정 기록만 검증한다. 현재 제안 저장·확정 기능이 있으므로 새 쓰기 도구 구현은 필요하지 않다. 가상 제안·근거 생성과 실제 확정은 확인된 격리 개발 DB 및 해당 동작의 별도 승인을 받은 뒤 진행한다. 반려는 확정으로 바뀌지 않는지 보는 대조 사례이며 대표 확정과 혼동하지 않는다. 이번 기준 승인은 실제 저장·확정 실행 승인이 아니다.

후속 구현 대상: agent-chat.tsx, agents/chat-runs.ts, API chat route, 해당 tests. 상태는 모델의 문장이 아니라 서버가 확인한 실행 기록에서 온다. 이번 기준 개정은 제품 코드를 바꾸지 않는다.
