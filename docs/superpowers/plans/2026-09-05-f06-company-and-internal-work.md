# F06 설계안 — 회사·자체 사업 업무

상태: **B안으로 확정. 2026-09-05 대표가 골랐고 개발 DB 변경도 승인했다.** · 계획 원본은 [개선 계획](2026-09-05-measurable-improvements.md)의 F06 절

> 🔴 **착수하고 나서 알게 된 것 — 사업 표는 이미 있다.**
> `ventures` 표가 이미 있고 매출 원장·비용 원장·에이전트가 그것을 쓴다. 에이전트에는
> 「프로젝트 또는 사업 중 하나에만 붙는다」는 규칙도 이미 있다.
> B안의 「사업 표를 새로 만든다」는 **필요 없다.** 업무를 그 표에 이어 붙이기만 하면 된다.
> 아래 B안 설명은 그 사실을 모르고 쓴 것이라 비용을 부풀려 적었다. 실제로 한 일은
> 마이그레이션 1개(업무에 유형 열과 사업 열 추가, 고객사·프로젝트 칸을 비울 수 있게)다.
> **「이미 있나」를 먼저 보지 않고 표부터 그린 것이 이 문서의 잘못이다.**

## 왜 지금 못 하나

업무를 담는 표가 **프로젝트와 고객사를 둘 다 반드시 요구한다.**

| 표 | 비울 수 없는 칸 |
| --- | --- |
| 업무(tasks) | 프로젝트, 고객사 |
| 프로젝트(projects) | 고객사 |

그래서 「사업자등록 서류 준비」나 「자체 앱 다음 판 출시」 같은 일을 넣으려면 **없는 고객사를 하나
만들고, 그 밑에 없는 프로젝트를 하나 만들어야 한다.** 계획서 F06-01이 「고객사 없는 유형은 가짜
고객사 생성 불필요」라고 못 박은 것이 바로 이 자리다.

「사업」이라는 개념은 지금 제품에 없다. 사업자등록번호 같은 칸이 있지만 그건 회사·고객사의 정보이지
업무를 묶는 단위가 아니다.

**결론 — 스키마를 바꾸지 않고는 F06을 만들 수 없다.** 이 문서는 무엇을 어떻게 바꿀지 정하기 위한 것이다.

## 이 문서가 아닌 것

- 구현이 아니다. 승인 전에는 코드도 마이그레이션도 쓰지 않는다.
- 마이그레이션 실행 승인이 아니다. 실행은 `CORELOOM_DATABASE_HOST`로 확인된 DB에만 돌고, 그 값은 사람이 확인해 적는다.

## 두 가지 길

### A안 — 업무에 유형을 붙이고, 고객사·프로젝트 칸을 비울 수 있게 한다

바꾸는 것

- 업무 표에 **유형** 칸을 더한다: 회사 운영 · 자체 사업 · 고객사 프로젝트
- 업무의 프로젝트·고객사 칸을 **비울 수 있게** 한다
- 데이터베이스가 직접 막는다 — 유형이 고객사 프로젝트면 두 칸이 반드시 있어야 하고, 나머지 두 유형이면 반드시 비어 있어야 한다(CHECK 제약)
- 자체 사업이 여럿이면 이름을 글자로 적어 구분한다

| | |
| --- | --- |
| 마이그레이션 | 1개 |
| 새 표 | 없음 |
| 기존 자료 | 그대로. 이미 있는 업무는 전부 「고객사 프로젝트」 유형이 된다 |
| 손대는 코드 | 업무를 읽고 쓰는 8곳(등록·목록·상세·대시보드·프로젝트 화면·에이전트 화면 등) |

**약한 곳** — 자체 사업이 여러 개가 되면 이름을 글자로 적는 방식이 흔들린다. 같은 사업을 조금 다르게
적으면 다른 사업이 된다. 그때 다시 표를 만들어야 한다.

### B안 — 사업을 표로 만든다

바꾸는 것

- **사업 표**를 새로 만든다(회사 운영, 자체 앱 각각이 한 줄)
- 업무에 사업 칸을 더하고, 유형에 따라 사업 또는 프로젝트 중 하나에 붙게 한다
- 데이터베이스가 「둘 중 하나에만 붙는다」를 직접 막는다

| | |
| --- | --- |
| 마이그레이션 | 2개(표 신설, 업무 칸 추가) |
| 새 표 | 1개 |
| 기존 자료 | 그대로 |
| 손대는 코드 | A안의 8곳 + 사업 등록·목록 화면 |

**강한 곳** — 자체 앱이 여럿이어도 흔들리지 않는다. 나중에 사업별 매출·비용을 묶을 때도 이 표가 쓰인다.
**약한 곳** — 지금 자체 사업이 하나뿐이면 표 하나를 위해 화면 한 벌을 더 만드는 셈이다.

## 어느 쪽을 권하나

**자체 사업이 지금 하나면 A안, 둘 이상이거나 곧 늘어날 것 같으면 B안.**

이건 코드가 아니라 사업의 사실이라 대표만 안다. 계획서 F06-02가 「워크스페이스·**사업**·프로젝트 범위」를
검사하라고 적은 것을 보면 B안 쪽을 염두에 둔 듯하지만, 그때는 아직 후속 후보였다.

## 완료 기준 (두 안 공통)

계획서의 검사 두 개를 그대로 쓴다. 목표를 바꾸지 않는다.

| 검사 | 통과 기준 | 어떻게 잴 것인가 |
| --- | --- | --- |
| F06-01 | 세 유형 업무 등록·재조회 3/3 | 각 유형으로 가상 업무를 만들고 다시 조회해 내용과 연결이 같은지 대조. **고객사 없는 유형에서 가짜 고객사를 만들지 않았음을 함께 확인** |
| F06-02 | 잘못된 유형 간 연결·무권한 조회 0건 | 회사 운영 업무에 프로젝트를 붙이려는 시도, 남의 워크스페이스 업무를 조회하려는 시도 등 음성 사례 |

여기에 더한다.

- 기존 업무가 하나도 사라지거나 유형이 잘못 붙지 않는다(마이그레이션 전후 개수·내용 대조)
- 대시보드의 프로젝트 카드가 회사 운영·자체 사업 업무를 남의 프로젝트 것으로 끌어오지 않는다
  (F05-03에서 이름 매칭을 프로젝트 번호 매칭으로 고쳤다. 그 규칙이 새 유형에도 지켜지는지)

## 실제로 한 일 (2026-09-05)

- `ventures`를 그대로 쓴다. 새 표 없음
- 업무에 유형 칸(회사 운영·자체 사업·고객사 프로젝트)과 사업 칸을 더하고, 고객사·프로젝트 칸을 비울 수 있게 했다
- 데이터베이스가 유형과 연결을 직접 맞춘다(`tasks_kind_link_ck`). 코드에도 같은 규칙이 있고, 그 둘이 어긋나기 쉬우니 문구를 바꿀 때 함께 본다
- 기존 업무는 전부 「고객사 프로젝트」로 남는다. 하나도 안 바뀐다

### 마이그레이션을 손으로 쓴 이유

`drizzle-kit generate`가 만든 파일이 **표 4개와 칸 수십 개를 새로 만들려 했다.** meta 스냅샷이
0018에서 멈춰 있어 그 도구가 0019~0031이 만든 것을 「없는 것」으로 보기 때문이다. 그대로 돌렸으면
이미 있는 표에 부딪혀 깨졌다. 0019~0031도 같은 이유로 손으로 쓰여 있다.

**다음 사람에게** — 이 저장소에서 `drizzle-kit generate` 결과를 그대로 믿지 마라. 만든 SQL을 열어
내가 바꾼 것만 들어 있는지 확인하고, 아니면 손으로 써라. 스냅샷을 정합하게 되돌리는 일은 아직 안 했다.

2026-09-05에 0033도 같은 이유로 손으로 썼다. **이 함정은 고쳐질 때까지 계속 나온다.**

## 승인이 필요한 것

1. ~~A안과 B안 중 하나~~ → **B안으로 정해졌다**(2026-09-05)
2. ~~개발 데이터베이스 스키마 변경~~ → **개발 DB만 승인됐다**(2026-09-05). 운영 DB는 아니다
3. 남은 것 — 마이그레이션을 실제로 돌리기 전에 **접속 대상이 개발 DB가 맞는지 대표가 그 자리에서 확인**한다

승인 뒤 순서는 이렇다. 마이그레이션 초안 → 대표가 접속 대상을 확인 → 개발 DB에만 실행 → 코드 → 검사 → 문서.

## 하지 않을 것

- 운영 데이터베이스는 건드리지 않는다
- 기존 업무의 유형을 짐작해 나누지 않는다. 전부 「고객사 프로젝트」로 두고, 옮길 것은 사람이 옮긴다
- 이 기회에 다른 표를 손보지 않는다. 매출·비용·견적에도 같은 제약이 있지만 이번 범위가 아니다
