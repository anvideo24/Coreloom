# F03-03 / F03-02 승인 검토 5사례 — 고정 정답표

> **주의 — 이 문서는 시험 정답을 담고 있습니다.** 대표(시험 응시자)는 시험 전에 이 문서를 보면
> 안 됩니다. 이 문서는 시험 감독(개발자 또는 시험을 준비하는 사람)만 봅니다.
> 모든 인물·회사·금액·날짜는 **가상 데이터(SYNTHETIC)**이며 실제 고객·거래와 무관합니다.

## 이 문서의 용도

1. **F03-03 자동 시험** (`apps/web/tests/approval-gates.test.ts`) — 아래 5사례를 그대로
   fixture로 만들어, 확정 직전 화면(`ApprovalReviewCard`)이 실제로 대상·금액·증빙·결과
   네 가지를 정확히 보여 주는지 코드로 대조한다.
2. **F03-02 사람 판단 시험** — 대표가 이 5사례를 승인함(대기함)에서 골라 승인/반려를 판단하는
   시험. 이 문서의 "정답"란은 대표에게 보여주지 않고, 시험 후 채점에만 쓴다.

## 시험 절차 (F03-02)

1. **연습 1회**: 이 표에 없는 별도의 쉬운 가상 사례 1건으로 화면 조작 방법(승인 체크박스,
   반려 사유 입력 등)을 먼저 익힌다. 연습 결과는 채점하지 않는다.
2. **순서 섞기**: 본 시험에서는 아래 5사례를 승인 대기함에 넣되, 표에 적힌 1~5 순서 그대로
   보여주지 않는다. 매번 무작위로 순서를 바꾼다(같은 사람이 두 번째 볼 때도 다시 섞는다).
3. **본시험**: 대표는 각 사례를 열어 대상·금액·증빙·결과를 확인하고 승인 또는 반려를
   선택한다. 반려 시 이유를 한 줄 적는다.
4. **채점**: 5사례 모두 정답(승인/반려)과 일치해야 "오판 0건"이다. 이유가 정답표의 함정
   요소를 짚었는지도 함께 확인한다(예: "증빙 없음"을 근거로 반려했는가).

사례를 **찾는** 속도는 이 문서가 아니라 [탐색 시험 10건](approval-search-cases.md)이 잽니다(F03-01).
여기 5사례는 찾은 뒤의 **판단**을 잽니다.

## 5사례

### 사례 1 — 비용 확정 (expense) · 대조군(함정 없음)

| 항목 | 값 |
| --- | --- |
| 대상 | 홍보 배너 제작 · 가상 광고사 A |
| 금액 | KRW 1,200,000원 |
| 증빙 상태 | 메모 있음: "세금계산서 수령 완료, 발주서 첨부 확인함" |
| 발생일 / 지급 예정일 | 2026-08-20 / 2026-09-10 |
| 예상 결과(확정 시) | 비용 확정 — 금액 고정, 자동 이체·세금계산서 발행은 시스템에 없음 |

**정답: 승인.** 금액·증빙·일정이 서로 어긋나지 않고, 지급 예정일이 도래했으며 증빙 메모가
실제 확인 사실을 담고 있다. 반려할 근거가 없다.

**함정 요소:** 없음(비교 기준이 되는 정상 사례).

---

### 사례 2 — 매출 확정 (revenue) · 함정: 금액 불일치

| 항목 | 값 |
| --- | --- |
| 대상 | 가상 프로젝트 베타 · 가상 고객사 B |
| 금액(화면 표시) | KRW 3,300,000원 |
| 증빙 상태 | 메모 있음: "견적서 v2 기준 계약 금액 3,000,000원(부가세 별도)" |
| 발생일 / 정산일 | 2026-08-25 / 2026-09-15 |
| 예상 결과(확정 시) | 매출 확정 — 금액 고정, 세금계산서 발행 없음 |

**정답: 반려.** 화면에 표시된 확정 금액(3,300,000원)과 증빙 메모에 적힌 계약 금액
(3,000,000원)이 서로 다르다. 300,000원 차이의 근거가 증빙에 없으므로, 대표는 원인을
확인하기 전까지 확정해서는 안 된다.

**함정 요소:** 금액 불일치 — 화면 금액과 증빙에 적힌 금액이 어긋난다.

---

### 사례 3 — 입금 확인 (billing) · 함정: 증빙 없음

| 항목 | 값 |
| --- | --- |
| 대상 | 가상 고객사 C · 가상 계약 감마 · 중도금 |
| 금액 | KRW 5,000,000원 |
| 증빙 상태 | **없음** — 메모 없음, 청구번호 없음, PO 없음. 입금 예정일만 존재 |
| 청구일 / 입금 예정일 | 2026-08-01 / 2026-09-01(이미 지남) |
| 예상 결과(확정 시) | 입금 확인 — 금액 고정, 세금계산서 발행 없음 |

**정답: 반려(보류).** 입금 예정일이 지났다는 사실만으로는 실제로 통장에 입금됐다는 증거가
되지 않는다. 증빙 칸이 "증빙 없음"으로 정직하게 비어 있으므로, 대표는 통장 입금 내역을
직접 확인한 뒤에만 확정해야 한다. 예정일이 지났다고 곧바로 승인하면 오판이다.

**함정 요소:** 증빙 없음 — 화면에 예정일만 있고 실제 입금을 증명하는 자료가 없다.
(참고: 이 시험을 준비하며 실제로 "예정일"이 증빙 칸에 섞여 표시돼 증빙 없음이 가려지는
결함을 발견해 고쳤다. 아래 "발견한 결함" 참고.)

### 사례 4 — 계약 체결 (contract) · 함정: 이미 확정된 건

| 항목 | 값 |
| --- | --- |
| 대상 | 가상 계약 델타 · 가상 고객사 D |
| 금액 | KRW 8,000,000원 |
| 증빙 상태 | 날인 원본 위치 있음: "회사 문서함/계약/가상고객사D-날인본.pdf" |
| 현재 상태 | **이미 "체결(executed)" 상태** — 승인 대기함에 중복으로 다시 뜬 항목 |
| 예상 결과(재확정 시도 시) | 이미 최종 계약으로 체결됨 — 재확정 불가 |

**정답: 반려.** 이 계약은 이미 체결이 끝났다. 승인 대기함에 다시 뜬 것은 새로고침 지연이나
중복 알림일 뿐, 실제로 확정할 새 내용이 없다. 이미 체결된 건을 다시 확정하려는 시도는
그 자체가 위험 신호이며, 대표는 상태 표시("체결")를 보고 반려해야 한다.

**함정 요소:** 이미 확정된 건 — 중복 확정 시도. 제품 코드는 `executeContract`가
"Executed contracts cannot be changed"로 이를 막는다(F03-04와 연결).

### 사례 5 — AI 제안 확정 (proposal) · 함정: 권한 없는 요청(근거 불일치)

| 항목 | 값 |
| --- | --- |
| 대상(제안 대상 고객사) | 가상 고객사 E · 가상 프로젝트 제타 |
| 제안 내용 | "다음 할 일: 가상 고객사 E에 v2 견적서를 이번 주 금요일까지 발송" |
| 근거 기록 | 통화 · 2026-09-02 14:00 · 제목 "가상 고객사 F 정기 통화" (원문 링크 없음) |
| 예상 결과(확정 시) | 제안 확정 — 공식 결정으로 남음 |

**정답: 반려.** 제안이 대상으로 삼은 고객사는 "가상 고객사 E"인데, 근거로 첨부된 통화
기록의 제목은 "가상 고객사 F 정기 통화"로 서로 다른 고객사를 가리킨다. AI가 잘못된 통화를
근거로 잘못 배정했을 가능성이 있다. 원문 링크도 없어 즉시 대조할 수 없으므로, 대표는
근거 원문(Recho 원본)을 직접 찾아 대상 고객사가 맞는지 확인하기 전까지 반려해야 한다.
AI 제안은 초안일 뿐이며, 근거와 대상이 어긋난 채로 확정하면 AI가 스스로 판단 권한을 넘어선
결정을 대표 이름으로 공식화하는 셈이 된다.

**함정 요소:** 권한 없는 요청(근거 불일치) — 제안 대상과 근거 기록의 대상이 다르다.

## 발견한 결함 (F03-03 작업 중 정정)

5사례를 실제 화면 로직으로 대조하는 과정에서, 비용·매출·입금 확정 화면의 "증빙" 칸이
**메모(진짜 증빙)가 없어도 지급/정산/입금 예정일을 자동으로 채워 넣어 "증빙 없음"이
한 번도 뜨지 않던** 결함을 찾았다(사례 3이 이 결함을 그대로 드러낸다). 예정일은 이미
화면의 "금액과 일정" 칸에 별도로 나오고 있어 증빙과 중복이었고, 실제 증빙이 없는 건도
있는 것처럼 보이게 만들었다. 세 화면(`expenses/[entryId]/page.tsx`,
`revenue/[entryId]/page.tsx`, `billings/[billingId]/page.tsx`)에서 증빙 칸을 메모(및
청구번호)로만 구성하도록 고쳐, 진짜 증빙이 없을 때는 "증빙 없음"이 그대로 드러나게 했다.
계약 체결 화면(`contracts/[contractId]/page.tsx`)은 날인 원본 위치 유무만으로 증빙을
판단하고 있어 애초에 이 결함이 없었다.

## 화면 연결 현황 (Task C)

| 종류 | 상세 화면 | ApprovalReviewCard 연결 |
| --- | --- | --- |
| 비용 확정 (expense) | `/expenses/[entryId]` | ✅ 연결됨 |
| 매출 확정 (revenue) | `/revenue/[entryId]` | ✅ 연결됨 |
| 입금 확인 (billing) | `/billings/[billingId]` | ✅ 연결됨 |
| 계약 체결 (contract) | `/contracts/[contractId]` | ✅ 연결됨 |
| AI 제안 (proposal) | `/proposals/[proposalId]` | ❌ **연결 안 됨** — 확정/반려 버튼은 있으나 대상·금액·증빙·결과 요약 카드가 없다 |
| 에이전트 요청 (agent_work) | `/agents/[agentId]` | ❌ **연결 안 됨** — 요청·입력·결과는 텍스트로 나열되지만 표준 검토 카드는 아니다 |

화면 추가는 범위가 커서 이번 작업에서는 진행하지 않았다. 대상 화면에 카드를 붙일지는
별도로 결정한다.
